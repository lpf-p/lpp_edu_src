# 资产存在性判定 · 覆盖率账本 · 判据留痕（永久）

> **本文件解决三个"测不深"的病根**（2026-09-18 由一次十四轮实战被动总结，见 §10 溯源）：
> ① 一开始就把不存在的资产当资产，**方向错了，后面再努力也深不到哪去**；
> ② 测到最后**说不出"到底测完了没有"**，于是既不敢收工、也无法升链；
> ③ 判据被推翻时**静默改口**，下次换个人（或换个会话）重新踩同一个坑。
>
> **定位：进站前的前置闸。** 不改 `dig-scope-workflow.md` §4 的进站打法，只在它前面加一步：
> **先判这台存不存在 → 只对"确证存在"的做全类型矩阵。**
> 与 `batch-verify-discipline.md` 分工：那份管**批量扫描的假阳性**，本文件管**单台资产的存在性**；基线规则互补，不重复。
>
> ⚠️ **本文件的产出属「判据 / 认知」，不是漏洞、也不是手法 —— 不受 `hunt-iter.md` 的漏洞门槛约束。**
> 门槛管的是"手法进短表"；判据类产出**不进短表**，落点就是本文件（见 §9 与 `hunt-iter.md`「落哪」格）。

---

## 0. 一句话

**状态码完全不可信 —— 403 ≠ 受保护，404 ≠ 不存在，200 ≠ 有内容。只认响应体，且必须与同批实时基线逐字节比对。**

---

## 1. 为什么要立这个闸（三种骗法各踩一次的实录）

| 状态码 | 当时的误读 | 实测真相 |
|---|---|---|
| **403** | "网关拦截 ⇒ 资产受保护 ⇒ 高价值后台" | 泛解析的**默认 vhost** 对任何名字都回 403；候选主机与**随机不可存在主机名**的响应体 **SHA1 逐字节同源** ⇒ 不构成"资产存在"的任何证据 |
| **404** | "路径不存在 ⇒ 这台没东西" | **两个真实站点就藏在 404 后面**：一个回 1250B 自定义错误页 + 引用签名脚本，一个走独立 nginx 548B 页（`Server: nginx` ≠ 站点默认的 `openresty+`） |
| **200** | "有内容 ⇒ 存活资产" | 一台 200 / 641B 返回的是**通用错误模板**（`Maybe this page moved?` 一类）⇒ **软 404**，应从存活清单里划掉 |

**⇒ 只认响应体。** 任何单靠状态码、单值 `Content-Length`、`last-modified`、`Server` 字符串下结论的做法，本文件一律判**无效**。

**⇒ 闸的价值：** 这一步不做，你会把 80% 的精力花在**不存在的资产**上（"测了半天没洞"的真实原因常常不是手法不行，是**这台根本没有后端**）；同时又会**漏掉**藏在 404/502 后面的真站点。

## 2. 双轨判据（本文件核心技术）

**两条轨都要取，但地位不同：响应体是主判据，CNAME 是辅助判据。**

### 轨 1（主）· 响应体逐字节同源比对

- 算法：`sha1(响应体)`，与**同批实时取得**的基线比对。
- **同批实时 = 硬约束**：基线**禁止**硬编码历史哈希、**禁止**跨天取、**禁止**从报告里抄。必须与候选主机在**同一批请求**里现场取。
- **基线要有两条（缺一不可）**：

| 基线 | 怎么取 | 回答什么问题 |
|---|---|---|
| **主机级基线** | 随机生成、**绝不可能存在**的主机名（`zzz-<16位随机字母数字>.<根域>`）的 `GET /` | 这台主机名**有没有被边缘登记** |
| **路径级基线** | 必然不存在的路径（`/__definitely_not_exist_abc123/`，沿用 `batch-verify-discipline.md` §1.1） | 这台 host 的**默认错误页**长什么样 |

- 判定表：

| 候选 SHA1 | 结论 |
|---|---|
| **≠ 两条基线** | **异形 ⇒ 确证存在**（哪怕状态码是 404 / 403 / 502） |
| **= 主机级基线** | **未登记 / 走默认 vhost** |
| **= 路径级基线 ≠ 主机级基线** | 走默认源站，**存在性不确定** |

### 轨 2（辅）· CNAME 形态

```
独立记录（{host}.<cdn 域>）  →  该主机名被边缘平台【显式登记】
                                 （是充分条件，但【不证明后面有应用】）
泛记录（{根域}.<cdn 域>）    →  【不可判定】（≠ 不存在）
```

**两个方向的反例（必须记住，否则会把判据用反）：**

| 反例 | 现象 | 它打破了什么假设 |
|---|---|---|
| 泛记录 **+** 框架异常页（Symfony / Laravel 报错页） | 主机名走泛记录，后面却**确有应用** | 打破「泛记录 ⇒ 不存在」 |
| 独立记录 **+** 默认源站页 | 有独立 CNAME，后面却是默认错误页 | 打破「独立记录 ⇒ 有应用」 |

**⇒ CNAME 判据是「充分不必要」。** 它只能回答"**被登记了吗**"，不能回答"**后面有东西吗**"。

### 四象限（把两条轨合起来）

| CNAME | 响应体 | 结论 |
|---|---|---|
| 独立记录 | 异形（≠ 任一基线） | ✅ **确证存在** |
| 独立记录 | 默认页 | 🟡 **已被边缘登记，无独立后端** |
| 泛记录 | **异形** | ✅ **确证存在**（单凭响应体即可定案，无需 CNAME） |
| 泛记录 | 默认页 | ⚠️ **不可判定**（≠ 不存在） |

> ⚠️ **第四象限的措辞是硬约束**：泛记录**不能排除**厂商以「泛域名 + 按 Host 回源规则」提供服务（该方式**不改 DNS**）。
> 所以只能写**"不可判定"**，**禁止**写"不存在"，**禁止**在提交材料里声称"资产真实存在" ——
> 厂商一核 DNS 泛解析就能反证你的判断，等于把整份报告的可信度搭进去。

## 3. 判据本身也会错：三条禁令（每条都有实测反例）

1. **禁止退化为关键词匹配。**
   实测假阳性：用 `sf-reset` / `Exception` 一类字符串判"是不是 Symfony 应用" ⇒ 该字符串**本就在 Symfony 默认 404 模板自身里**，必然误中。
   **修法**：只认 **SHA1 同源** / **结构性证据**（与 `batch-verify-discipline.md` §1.2 同精神），**不认子串**。
2. **禁止用 IP 判 CDN 归属。**
   CDN 多节点，**同一条 CNAME 两次解析会得到不同 IP**（实测同主机两次分别得 `36.x` 与 `1.x`）—— 曾用"IP 集合"判据一次**误判 8 台**为"独立源站"。
   **修法**：认边缘平台**只看 CNAME 后缀形态**（§4）。
3. **禁止用 `last-modified` / 单值长度判源站。**
   实测反例：两台主机 body SHA1 **完全相同**（= 同一默认页），却只有一台带 `last-modified` ⇒ 该头只是**缓存标记**，不是源站特征。
   **修法**：回到 SHA1。

## 4. 认边缘 / CDN 平台：只看 CNAME 后缀（不看 IP）

| CNAME 后缀 | 平台 | 附带判据 |
|---|---|---|
| `*.eo.dnse0.com` | 腾讯 **EdgeOne** | `server: openresty+`（频道类）/ `TencentEdgeOne`（应用类） |
| `*.f1.zlibs.com` | **网宿**系（泛记录与独立记录**都可能**是它） | 泛记录形态 = `{根域}.f1.zlibs.com` |
| `*.txlivecdn.com` | 腾讯云**直播** CDN | `server: MC_VCLOUD_LIVE` |
| `*.w.kunlunca.com` | **阿里云** CDN | `server: Tengine` + `via: cache*.l2cn*` |
| `ksyun-*` | **金山云** | — |
| `*.myqcloud.com` / 返回 `AccessDenied` 的 404 | 腾讯云 **COS** | — |

**判泛解析（`recon-fingerprint-cdn-wildcard.md` §3 的补充）：** 若 `*.target.com` 的 CNAME **统一指向同一条**（如 `target.com.<cdn>.com`），即可判"这一族都是泛记录"；对照组务必取**另一个根域**（确认自己没有泛解析），否则会把平台行为当成自己发现的证据。

## 5. 泛解析环境下【失效】的旧判据（照抄会错）

| 旧判据 | 为什么失效 | 正确说法 |
|---|---|---|
| 「不解析 / NXDOMAIN ⇒ 没这台」 | 泛解析下**不存在"不解析"的名字**，任何名字都解析成功 | 该判据**整体失效**，不能再用 |
| 「TLS 握手失败 ⇒ 主机不可达」 | 实际是**无站点证书** | ⇒ **确证未配置**（这是**正向**证据，比 404 更强） |
| 「403 ⇒ 受保护」 | 默认 vhost 也回 403 | ⇒ 见 §1 |
| 「404 ⇒ 不存在」 | 真站点也回 404 | ⇒ 见 §1 |
| 「200 ⇒ 存活」 | 软 404 也回 200 | ⇒ 见 §1 |

**配套：** 判泛解析这件事本身**每个种子都要过**（`recon-fingerprint-cdn-wildcard.md` §3.1），且**逐层判**（`*.target.com` / `*.a.target.com` 各自判一次）。

## 6. 覆盖率账本 —— "测完了"的**唯一**依据

**没有账本 = 不许说测完。** 账本两张表，缺一不可。

### 表 A · 资产级（本文件新增 · 锁面有清单时必建）

落盘路径：`资产/资产账本.md`

```
| # | 主机 | 状态码 | SHA1(体) | CNAME 形态 | 判定 | 依据 | 已做测试 | 备注 |
```

- **`判定` 列只允许四个值**：`确证存在` / `已被边缘登记·无后端` / `不可判定` / `确证未配置`。
- **收工判据：`判定` 列无空缺。** 任何主机不许留空、不许写"待定"、不许写"看情况"。
- 表格**外**单列一节 **「确证存在 → 本轮做了哪些矩阵 / 哪些记 N/A + 原因」** ——
  ⚠️ **"存在" ≠ "测过"**，两列必须分开记，否则账本会退化成"我没漏主机"的自证。

### 表 B · 种子级（沿用 `dig-scope-workflow.md` §1.4）

`资产/种子队列.md` 的 **pending 面 = 0** 才算整场收工（`blocked` 不算 pending）。

### 收工三联（三张表都要清，缺一条不许收）

```
[ ] 表 A：资产级「判定」列无空缺
[ ] 表 B：种子队列 pending = 0
[ ] 确证存在的资产，逐个有矩阵记录（或无入口 + 写明原因）
```

**⇒ 这三条就是「把测试目标完全测试」的可操作定义。** 达到它之前，禁止以"看起来没什么可测了"收尾。

## 7. 判据被推翻时的留痕制度（本次深度的一半来自这里）

**判据不是一次写对的。** 实测：主判据被推翻 **3 次**（IP 判据 → CNAME；`last-modified` → SHA1；关键词匹配 → SHA1 同源）。

制度：

1. **失败版本的文件不删。** 命名上区分（`*_fix` / `*fix2` = 修正版），**失败版原样留在 `{名}_dig/`** —— 它是下次不再犯的**唯一凭据**，也证明"结论是怎么被推翻的"。删了 = 下次重新踩。
2. **判定留痕成文**：每次推翻写进 `{名}_dig/判据演进.md`，一段一条，格式固定：

   ```
   旧判据：…      反例：…（实测）      新判据：…
   ```

3. **禁止"静默改口"**：报告里改了结论，必须同时留一条 **"原判 X，因 Y 改为 Z"**，写明依据。
   禁的是模式**装看不见旧结论**、直接改数。

> 与 `hunt-iter.md`「假点列」的区别：假点记的是"这种**形态**不是洞"；本节的留痕记的是"我这次**判据用错了**"。
> 前者是知识，后者是**校准**，两者不合并。

## 8. 范围判定：「页面在范围内」≠「页面引用的主机也在范围内」

从**在范围内**的页面提取到**范围外**引用（第三方 SDK 域、低代码平台实例域、CDN 主域、对象存储域）时：

```
只登记 → 零请求。
写进「绝对不触碰」清单，并注明「由哪个在范围页面引用」。
```

**禁止**因为"它出现在我的目标页面上"就去请求它。

**同理 —— 储备项的"永久关闭"要有正确措辞：**
低代码 / DP 平台的接口**真实落点**常在 `rs*.` / `*-rsmp*` / 平台实例域一类主机上，若**在范围外**，则该项**永久关闭**，且关闭理由必须写成
**"落点已完整枚举、全部在范围外、零请求"**，而不是"没找到落点"。
（前者是**已完成**的判定；后者听起来像还有余地，会把下一个人重新引回这条死路。）

## 9. 落点与边界（与 `hunt-iter.md` 的分工，别混）

| 产出类型 | 落点 | 受漏洞门槛约束吗 |
|---|---|---|
| 手法（认 A → 打 B） | `知识库/打穿短表.md` + 对应模块 | **受**（须已落报告的高危/严重） |
| 漏洞 | 任务 `报告/` | 受 `vuln-report-format.md` 等级口径 |
| **判据 / 认知 / 方法论修正 / 存在性判定 / 覆盖率账本** | **本文件**（`rules/asset-existence-and-coverage.md`） | **不受**（本文件即权威落点） |

⚠️ **判据类产出不进短表**，也**禁止**因为"不是漏洞"就丢掉 —— 丢掉它，下次换站还会把 403 当资产存在。

## 10. 溯源（这批判据怎么来的）

来自 2026-09-17~18 对某门户站群的一次**十四轮**授权 SRC 测试。该目标的形态正是本文件最适用的那一类：

- 厂商公布 **78 项资产清单**（锁面），清单内相当一部分是**空壳 / 默认页 / 未部署 / 泛记录**；
- `*.根域` **存在泛解析**（含一条对照组根域**无**泛解析）；
- 边缘由**多平台**承担（EdgeOne / 网宿 / 阿里 Kunlun / 腾讯云直播 / 金山云）。

十四轮的**可提交漏洞只有 16 项、最高 1 项中危** —— 但**历轮最值钱的产出全部落在判据层**（本文件 §1~§5），
且这些判据**按 `hunt-iter.md` 门槛一条都进不了库**（门槛只收"已落报告的高危/严重"）。
本文件即是给这类产出开的**合规落点**。

**判据演进时间线（失败版本全部保留，脚本未删）：**

| 判据 | 反例 | 结果 |
|---|---|---|
| IP 集合判 CDN | 同一 CNAME 两次解析出不同 IP | 误判 8 台 → 改 CNAME 判据 |
| `last-modified` 判源站 | 两主机 body SHA1 相同、只有一个带头 | 改回 SHA1 |
| 关键词（`sf-reset`）判框架 | 该串在框架默认 404 模板里 | 改 SHA1 同源比对 |
| 三层响应模型 | 泛记录主机确有应用（框架异常页） | 升级为**双轨四象限**（§2） |

## 11. 一句话（收口）

**先判存在，再谈测试；判不出存在就写"不可判定"，不许当真资产往上报。**
**判据要留痕，账本要清零 —— 这两件做到，才叫"把目标测完"。**
