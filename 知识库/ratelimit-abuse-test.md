# 接口滥用：限流绕过 / 验证码绕过 / 资源耗尽

> 定位：`logic-test.md` §2.3（短信轰炸）与 §4.1（账号枚举）的**正文**，以及 `password-reset-test.md` §五（限频）的**手法展开**。
> 这一类**单独交多为中低危**，但它是**爆破 / 枚举 / 接管的必要前提**——所以价值在于**并入主链**：「限频失效」让「验证码可枚举」变成「无限次尝试」。
> 冲突以 `rules/src-value-hunting.md`、`rules/dig-scope-workflow.md` §4.2.2 与 `rules/vuln-report-format.md` 为准。
> **实战案例（双向引用）** → `logic-web-cases.md` **§5.7 短信轰炸**（30 并发收到 28 条）、**§5.2 验证码爆破**、**§6 密码重置**（交易密码爆破见索引序号 72）、**§10.2 二要素/实名接口滥用**、**§10.5 邮箱轰炸绕过**；并发放大手法见 `logic-web-cases.md` §3.2 与 `race-condition-test.md` §5。

## 0. 价值定位（先想清楚为什么打）

| 单独看 | 并进链里 |
|---|---|
| 限频缺失 = 低危 | 限频缺失 + 验证码可枚举 = 高危 |
| 验证码 4 位无锁定 = 中危 | 4 位 + 无频控 + 身份字段不校验 = 严重 |
| 短信轰炸 = 低危 | 轰炸 + 可枚举号段 = 骚扰 + 隐私 |

**所以**：打这一类时，**同时记下它解开了哪一道门**，写进报告的「攻击链佐证」（见 `password-reset-test.md` §八）。

## 1. 限流识别

### 1.1 找限流点

| 功能 | 为什么关键 |
|---|---|
| 登录 | 撞库前提 |
| 发验证码 | 轰炸 + 爆破前提 |
| 密码找回 / 身份校验 | 枚举前提 |
| 注册 | 批量注册前提 |
| 评论 / 留言 / 举报 | 骚扰 |
| 导出 / 查询 | 资源耗尽 |
| 领券 / 抽奖 / 积分 | 薅羊毛 |

### 1.2 测阈值（先定量）

```bash
for i in $(seq 1 30); do
  curl -s -k -b s.txt -X POST "https://T/api" -d "..." | tr -d '\r\n'; echo
done
# 观察第几次开始返回「非法操作」「访问频繁」「请稍后再试」
```

**记录三件事**：第几次被拦、被拦的响应特征（文案 / 状态码 / 长度）、**多久恢复**。

### 1.3 账号枚举 / 用户枚举（三口差分对照）

枚举本身常是低危，但**配合限流失效**就是高危前提——所以放本篇，而不是单独一篇。

**三个入口各跑一次，diff 响应**：

| 入口 | 对照 |
|---|---|
| 注册（查重） | 已注册 vs 未注册 |
| 登录 | 账号存在 + 密码错 vs 账号不存在 |
| 找回 / 申诉 | 有账号返回内容 vs 无账号返回空 |

**看什么**（按漏判概率排序）：
1. 响应**长度**不同 —— 最容易漏，用 `wc -c` 比，不看内容
2. 响应**文案**不同 —— 「用户不存在」vs「密码错误」
3. 响应**字段**不同 —— 有/无脱敏邮箱、密保问题、验证码类型
4. 响应**状态码**不同
5. 响应**耗时**不同 —— 查了库 vs 没查（要连打多次取稳定值）

```bash
diff <(curl -s ... account=存在的) <(curl -s ... account=不存在) | head -40
```

**关键**：同 `password-reset-test.md` §3.5 —— **diff 两份响应**，差集里就是可枚举信号，不需要真的爆破出账号。

**假点**：响应完全一致（连耗时都一致）→ 无枚举。别把「接口统一返回请登录」当枚举——那恰恰是**没**枚举。

## 2. 限流绕过

### 2.1 换 IP 头（命中率最高）

服务端常取 `X-Forwarded-For` 当客户端 IP，却没验证真实来源。

```bash
for h in "X-Forwarded-For" "X-Real-IP" "Client-IP" "X-Client-IP" \
         "X-Originating-IP" "True-Client-IP" "Forwarded" \
         "X-Forwarded" "X-Forwarded-Host" "CF-Connecting-IP"; do
  r=$(curl -s -k -b s.txt -X POST "https://T/api" -H "$h: 1.1.1.1" -d "..." | tr -d '\r\n')
  echo "$h -> $r"
done
```
**若返回正常（非封禁文案）→ 该头可绕过。**

### 2.2 持续绕过验证（确认完全失效）

```bash
ok=0; blocked=0
for i in $(seq 1 25); do
  XFF="$((RANDOM%254+1)).$((RANDOM%254+1)).$((RANDOM%254+1)).$((RANDOM%254+1))"
  r=$(curl -s -k -b s.txt -X POST "https://T/api" -H "X-Forwarded-For: $XFF" -d "..." | tr -d '\r\n')
  [ "$r" != "false" ] && blocked=$((blocked+1)) || ok=$((ok+1))
done
echo "成功=$ok 被拦=$blocked"
# 25/25 成功 → 限频完全失效
```

### 2.3 号码 / 用户名变形

| 变形 | 示例 |
|---|---|
| 加前缀 | `13800138000` → `+8613800138000` / `008613800138000` |
| 加空白 | ` 13800138000` / `13800138000 ` / `%0913800138000` |
| 加分隔符 | `138-0013-8000` / `138 0013 8000` |
| 大小写 | 邮箱 `A@b.com` vs `a@b.com` |
| Unicode 全角 | `１３８００１３８０００` |
| URL 编码 | `%31%33%38...` |

**判定**：变形后**仍发到同一个号**但**绕过计数** → 绕过成立。

### 2.4 参数污染

```bash
phone=13800138000&phone=13800138001    # 后端取第一个发、取第二个计数
```
JSON 里同理：`{"phone":"a","phone":"b"}`

### 2.5 换入口（最容易被忽略）

同一功能常有**多个入口，限流各自独立**：
- App / H5 / 小程序 / PC 站点 / 开放 API
- 老版本接口（`/v1` 与 `/v2` 限流分开）
- 不同域名（业务域 vs 网关域 vs 开放平台域）

**打法**：先在 A 入口测阈值，被拦后**换 B 入口继续打**，看计数是否独立。

### 2.6 并发打窗口边界

限流基于时间窗（如「每分钟 10 次」）。在窗口边界（第 59-61 秒）**并发**打，计数可能重置。

### 2.7 其他

- 换会话（清 Cookie 重新拿）
- 慢速攻击（每次间隔略小于恢复时间）
- 换 `User-Agent`（有些 WAF 按 UA 计数）

## 3. 验证码绕过

> 找回链上的验证码另见 `password-reset-test.md` §二（明文回显 / 仅前端校验 / 服务端零校验）。本节是通用手法。

| 形态 | 打法 | 判定 |
|---|---|---|
| 万能码 | `000000` `111111` `123456` `888888` `666666` | 直接通过 |
| 回包带码 | 看响应体 / 响应头 / Set-Cookie | 有 `code` / `captcha` 字段 |
| 空码 / 删参 | 去掉 `code=` 整个参数 | 仍然通过 |
| 码不绑会话 | A 会话收的码，B 会话提交 | 通过 |
| 码不绑号 | A 号的码 + B 号的手机号 | 通过 |
| 码不失效 | 用过一次再发一次 | 第二次仍通过 |
| 码可复用 | 同一码用于不同流程 | 通过 |
| 仅前端校验 | 直接调下一步接口 | 不带码也能过 |

**最强证明**：全新会话里**从未请求验证码图**，直接提交任意值却通过（详见 `password-reset-test.md` §2.3）。

### 3.1 爆破可行性判定

4 位纯数字 = 10⁴，6 位 = 10⁶。**只有在限频失效时才有意义**——所以**先测限频**（§2），再谈爆破。

```bash
# 只做可行性验证，不做完整爆破
for c in 0000 0001 0002 ... ; do  # 控制在 100 次内
  curl -s -k -b s.txt -H "X-Forwarded-For: $((RANDOM%254+1)).1.1.1" \
    -X POST "https://T/api" -d "phone=13x&code=$c"
done
```

**红线**：控制在**功能验证量级（≤100 次）**，不做完整爆破、不做 DoS。

## 4. 短信 / 邮件轰炸

### 4.1 三种形态

| 形态 | 危害 | 判定 |
|---|---|---|
| 同号无限发 | 骚扰 | 连打 N 次都成功 |
| 换号发（号可枚举） | 骚扰 + 号段隐私 | 换号仍发 |
| **参数改号但仍发到固定号** | 可打任意号 | 改 `phone` 参数，消息到的还是原来那个号 |

### 4.2 测试纪律（重要）

- **只测 1-2 次证明无限制**，拿到「连续 N 次成功」的截图/响应即可
- **禁止真轰炸**真实号码（对齐 `logic-test.md` §2.3「内部略测限频」）
- 用自己的号 + 一个测试号，**不碰他人号码**
- 记录**响应内容**（是否都一样 / 是否暴露了短信模板 / 是否带验证码）

## 5. 资源耗尽

中低危为主，且**测试本身容易影响线上**，谨慎。

| 形态 | 打法 | 判定 |
|---|---|---|
| 深分页 | `page=9999999` / `offset` 巨大 | 响应极慢或 OOM |
| 大分页 | `pageSize=9999999` | 单次拉全表 |
| 批量导出无上限 | 导出接口无条数限制 | 一次导出全量 |
| 正则 ReDoS | 超长串喂给搜索/校验 | 单个请求 CPU 打满 |
| 压缩炸弹 | 小 zip 解压出巨大文件 | **谨慎，可能真打挂** |
| 图片/视频处理 | 超大图 / 畸形图 | 处理超时 |
| 递归/嵌套深度 | 深嵌套 JSON / XML | 解析耗尽栈 |

**红线**：**只做单请求验证**（打一次，观察到慢/报错即停）。**禁止并发压测、禁止持续打**。这类一般不收，只当佐证。

## 6. 账号体系滥用

| 形态 | 打法 |
|---|---|
| 无限注册 | 无手机验证 / 验证码可绕过 → 批量注册 |
| 批量领券 / 薅羊毛 | 同号重复领、换号领、并发领 |
| 邀请奖励自刷 | 自己邀请自己、循环注册 |
| 无限试用 | 反复开通试用 |
| 虚拟资产刷取 | 并发、重复提交（见 `race-condition-test.md`） |

**技巧**：注册时**参数最小化**——只留必填字段，看哪些字段其实没校验（对齐 `password-reset-test.md` §3.4 的「逐个独立性」思路）。

## 7. 别停提示

- 第一次被拦**别停**：换 IP 头、换入口、换号码格式，至少各试一次
- 限流看起来严**别停**：确认它是按 IP 还是按号——按号的话，换号就是绕过
- 验证码 6 位**别停**：先看它绑不绑会话、绑不绑号、过不过期
- 短信接口返回「发送成功」**别停**：看响应体里有没有验证码 / 有没有真实发出（对照不存在的号）
- 只能改自己账号**别停**：限流失效的证明在「请求次数」上，不需要碰到别人的号

---

## 8. 假点

- 限流**真实生效**（换头、换入口、换格式都拦）→ 无洞，停
- 响应文案是「发送成功」但**实际没发**（对照不存在号返回一样）→ 可能只是统一响应，不是洞
- 验证码**绑会话 + 绑号 + 单次有效 + 有频控** → 无洞
- 只测出「能连打 30 次」但**接口无任何敏感动作**（如查询公开数据）→ 低危或不收
- 深分页慢是因为**业务本来就这么慢**，不是你的 payload → 对照不带 payload 的请求时间

---

## 9. SRC 红线

- 请求量控制在**功能验证量级（≤100 次）**，**禁止** DoS / 压测
- **禁止**真轰炸他人手机 / 邮箱（只用自己可控的号，且 ≤2 次）
- **禁止**爆破真实账号（用不存在的号验证逻辑分支，注意账号锁定策略）
- **禁止**用并发打生产库、打导出接口拖全量数据
- 打完**改回**自己改过的东西（对齐 SKILL.md 安全红线）

## 10. 自检

- [ ] 是否先**定量**测了阈值（第几次被拦、多久恢复）？
- [ ] IP 头是否**逐个**试过（不止 XFF）？
- [ ] 是否试过**换入口**（App/H5/小程序/老版本接口）？
- [ ] 号码/用户名是否试过**变形**（前缀、空白、全角、编码）？
- [ ] 验证码四项（绑会话 / 绑号 / 失效 / 复用）是否都测了？
- [ ] 是否**先测限频再谈爆破**？
- [ ] 短信轰炸是否控制在 ≤2 次、只用自己的号？
- [ ] 资源耗尽是否**只做单请求验证**（没并发压测）？
- [ ] 是否记下了「这个缺陷解开了主链上的哪一道门」？
- [ ] 有没有超出 100 次请求 / 打到 DoS？

## 11. 一句话

**先定量再绕过；IP 头逐个试、入口换着打、号码变着形；验证码四项全测；先测限频再谈爆破；轰炸 ≤2 次只用自己的号；资源耗尽只打一次；价值在于写清它解开了哪道门。**
