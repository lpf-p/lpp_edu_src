# login-bypass-playbook

**登录框是 SRC 最高频的攻击面，也是最容易"以为测过了其实没测全"的地方。** 本文件是**通用手法**手册；`authbypass-test.md` 收的是**具体系统/具体口**的案例，两者互补不重叠。

> **实战案例（双向引用）** → `weak-password-cases.md`（ima `src报告/弱口令/` 25 条 → 20 份唯一 → 实读 19）：系统指纹 × 默认口令速查表、初始口令规则、怎么论证危害升档；另见 `middleware-unauth-test.md`（组件未授权面）。回查原文见 `ima-retrieval-index.md` §三。

认到登录框先跑本文件 §1 的 10 枪（几分钟的事），再去 `authbypass-test.md` 找对应系统形态。

**纪律**：弱口令**每系统只试 3~5 个**，不跑字典；中了立刻停手，够定性就够，**不要登进去翻数据**。

## §1 登录框十枪（按顺序打）

### 1. 删参数（最快，命中率不低）

拦截登录请求，**逐个删字段**再发：`password` `captcha` `verifyCode` `token` `code` `smsCode` `sign` `timestamp`。

```
原: username=admin&password=xxx&captcha=1234
删: username=admin&captcha=1234          ← 服务器没校验密码字段存在性就直接过
删: username=admin&password=xxx          ← 验证码字段没校验
```

成因：服务端用 `map.get("password")` 拿值后没判 null，或「有这个 key 才校验」的写法。
**变体**：把值改成空串、改成 `null`、改成数组 `password[]=a&password[]=b`（类型混淆）。

### 2. 操纵响应包

登录响应**在前端判定**时，改响应即可进。BP 勾 `Intercept Response`，或浏览器改。

```
403 Forbidden  →  200 OK
{"error":true,"message":"Invalid Token"}  →  {"success":true}
{"code":401}  →  {"code":0}
{"status":"fail"}  →  {"status":"ok"}
```

**判定是不是前端判定**：改完真的进去了、能看到登录后功能 → 是。**只改了显示、刷新又回登录页** → 是后端判定，这条不成立（假点）。

### 3. 分包验证（验证码单独一个请求时，必打）

很多登录是**两步**：先 `POST /checkCaptcha` 验验证码，再 `POST /login` 验账密。

**打法**：
1. 验证码填**错的**，发第一个请求
2. BP 拦响应，把 `{"success":false}` 改成 `{"success":true}`
3. 放行，第二个请求照发 → **验证码形同虚设**，可以无限暴破

**这是投暴破的前提**，不是洞本身。真洞要写成「验证码校验可被绕过 → 可无限制暴破」，并附暴破成功的证据（注意 §4 纪律）。

### 4. 验证码缺陷清单

| 缺陷 | 怎么验 |
|---|---|
| **可复用** | 同一个 captchaId + 值，连续发 3 次，都过 → 可复用 |
| **前端生成/前端校验** | 验证码值出现在 JS 或响应体里（不是图片） |
| **空值可过** | `captcha=` 空串直接发 |
| **万能码** | 试 `0000` `1111` `1234` `8888` |
| **无次数限制** | 错 10 次不刷新、不锁定 → 可暴破（配合第 3 条） |
| **响应里带答案** | 看获取验证码的接口响应/响应头/Cookie |

### 5. 默认凭据（老系统/中间件最高发）

```
admin/admin  admin/123456  admin/admin123  admin/888888  admin/12345
test/test  admin/1  admin/000000
系统名/系统名  系统名/123456  系统名@2024
```
高校/政务常见：`学号/学号`、`工号/工号`、`学号/身份证后6位`、`admin/学校缩写@年份`。
**只试 3~5 个**。中间件默认口令见 `middleware-unauth-test.md`。

### 6. 万能密码（SQL 注入型）

```
' or 1=1--    ' or '1'='1    admin'--    admin' #    ' or 1=1#    ") or 1=1--
```
老 PHP / ASP 站高发（WAF 也少）。中了就是**认证绕过 + SQL 注入**两个洞，**合并成一个报**（佐证合并不拆分）。

### 7. 目录爆破找"登录后才有"的页面

登录后的页面如果**自身没有鉴权**，直接访问 URL 就能进。用 ffuf / dirsearch 扫后台路径，或：
- 从 JS 里翻路由表（见 `js-reverse-guide.md` 流程七 影子 API）
- 从报错页/404 页的菜单残留里找

**判定**：直接访问能出数据 = 鉴权在前端/或在网关但没覆盖该 path（后者是 `redirect-ear-unauth.md` §2）。

### 8. 账号枚举差分（顺手做，常能单独成洞）

同一密码，换不同用户名，对比：

| 维度 | 说明 |
|---|---|
| **错误文案** | 「用户不存在」vs「密码错误」→ 直接枚举 |
| **响应长度** | 差几十字节也算 |
| **状态码** | 200 vs 401 vs 302 |
| **响应时间** | 存在的用户走哈希校验，明显慢（多测几次取中位数，**单次抖动不算**） |

**注意**：很多系统提示语统一成「用户名或密码错误」——这时**别放弃**，看长度和时间。

### 9. 状态码 / 跳转差异

- 成功 302 到 `/home`，失败 302 到 `/login?error=1` → **Location 本身就是差分**
- 成功 200 返 JSON，失败 200 返 JSON 但 code 不同 → 看 body
- **3xx + 响应体有内容** → 转 `redirect-ear-unauth.md`（PHP/Java 老后台重灾区）

### 10. JWT / 会话类

- **alg 改成 `none`**、删签名段
- **密钥爆破**：`qmPlus` `secret` `your-256-bit-secret` `changeit`（GVA 默认 `qmPlus`）
- **置空 token**：删 `Authorization` / `x-token` 头后是否返全量数据
- **RS256 → HS256** 算法混淆
- 详细见 `oauth-jwt-test.md`，这里只做快速试

## §2 顺序建议

```
1 删参数  →  2 改响应  →  3 分包/验证码  →  8 枚举差分
（这几条几分钟，收益最高）
    ↓ 都不中
5 默认凭据(3-5个)  →  6 万能密码  →  10 JWT
    ↓ 都不中
7 目录爆破找未鉴权页面  →  9 状态码差异
```

**别一上来就跑弱口令字典**——先做前 4 条，性价比高得多。

## §3 定级

| 结果 | 定级 |
|---|---|
| 能登录任意/指定账号，或完全绕过进后台 | 严重 / 高危 |
| 验证码可绕过 + 可暴破，且真的暴破出账号 | 高危 |
| 账号枚举（能批量确认哪些用户名存在） | 中危（很多 SRC 收，别当低危丢掉） |
| 仅改响应包但刷新即失效 | **不算洞**（假点） |

## §4 假点与红线

- **改响应包后刷新回登录页** = 只是前端显示，**不是洞**
- **验证码可复用但没证明能暴破成功** = 只报「验证码缺陷」中危，别吹成「可接管任意账号」
- **暴破**：只在 SRC 明确允许时做，且**控制次数**（几十次量级），不要打挂对方服务
- **别用真实用户名列表批量撞** —— 用 1~2 个自测账号证明可行性即可

## §5 一句话

**登录框先试「删、改、复用」这三招，再谈爆破。** 大多数登录框的问题不在密码强度，在校验逻辑本身。
