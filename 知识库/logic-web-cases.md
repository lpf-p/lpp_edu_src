### 2.1 直接改价（`price` / `amount` / `unitPrice` / `money`）

- **成因**：金额由前端提交，服务端"信任"该字段或只做非空校验，未与商品库单价/后端重算结果比对。
- **动作**：下单 / 提交订单 / 跳收银台三个包任一环节，把金额字段改小。
- **判定**：收银台实付金额随之变化 = 成立；若签名（`sign`）未绑定金额，则改价后仍可支付成功。
- **实战锚点**：
  - ToB CRM 商城「用户数加油包」单价 7980 × 3 → 改 `productList[].price:"0.01"`，实付 **0.03 元**拿到原价 15960 权益（`某厂家支付漏洞` / `百度支付漏洞`，两个目标是同一套逻辑）。
  - 微博博文头条推广 `GET /aj/pay/settleweibopay?nonfans=10000.00&money=10000.00&price=10000.00` → `nonfans` 改 `0.01` 仍下单成功，**0.01 元买万元推广**。
  - 百度页游充值 `GET /gpays/sdk/create_order?...&price=30&sign=3102ff3b...` → `price=1`，**1 元买 30 天月卡**（sign 未对金额做绑定）。
- **定级**：高（涉钱必高，实际多数评高危或严重）。

### 2.2 负数与正负叠加

- **成因**：数量/单价未做 `>0` 校验，参与乘加运算后总额变负。
- **动作**：`quantity=-1` 造负总额；或 A 商品 +30、B 商品 -10×2 使总价归零。
- **案例锚点**：`36-交易支付逻辑漏洞小总结`（余额支付数量改负 → 总额负 → 扣负得正，余额反增）；`支付逻辑漏洞.pdf`（`cnum=-90000000`）。

### 2.3 整数溢出（int32 边界）

- **成因**：金额/数量用 int32 存储或运算，超 `2147483647` 回绕。
- **动作**：支付金额 `2147483649` → 溢出为 **1**；数量取 `2147483647 / 单价 + 1` 制造溢出。
- **案例锚点**：`逻辑漏洞-月神.pptx`（明确写下 `2147483649` 溢出为 1 的算式）；`支付逻辑漏洞思路小集合`（最小/最大额溢出列为第 ⑧ 类必测）。

### 2.4 精度 / 四舍五入（"厘"被吞）

- **成因**：第三方支付只精确到「分」，服务端入账/出账时对第三位小数做了四舍五入，且**不回校实际扣款金额**。
- **动作**：提交 `0.019` / `1.005` 这类非整分金额，制造舍入方向的差额。
- **关键经验**：**充值端修了不代表提现端修了**——`支付漏洞四舍五入re` 就是充值端已修复、提现在 `/api/ms-trade/trade/redeem` 提交 `applicationamount=1.005`，界面显示 1.00 而银行卡到账 **+1.01**。
- **案例锚点**：`0到1逻辑漏洞-支付篇`（充 0.019 → 支付单显示 0.01 元 → 到账 0.02，错误码 `TOTAL_FEE_EXCEED` 可用于判别）；`4舍5入的支付漏洞`（同源）。

### 2.5 限购 / 购买数量限制绕过

- **成因**：限购只在**前端提示**或**提交前校验**，创建订单接口本身无数量校验，且已创建未支付订单不占用额度。
- **动作**（三种，逐级深入）：
  1. 浏览器多开 / PC + 移动端各开一个窗口，同时创建多笔未付订单；
  2. 抓「创建订单」包直接重放，每次拿新订单号；
  3. 支付路径可重放（末 6 位可爆破），配合解约反复刷。
- **实战锚点**：
  - `突破购买限制` / `某厂家突破购买数量`：`POST /cn/oapi/orders/web/trade/create` 无限重放，返回 `{"code":200,"data":"220412..."}` 每次新订单号。
  - `限制购买逻辑漏洞`：百度智能云学生套餐"限购 1 台"，多开创建多笔未付订单均可支付；云盘会员首月 6 元经 `SuperWap?qrcodeid=` 批量重付，**72 元买 406 天**。
- **定级**：中（业务 SRC 常见 40 币），时长可叠加时升为高。

### 2.6 支付状态与响应包篡改

- **成因**：支付成功与否由前端读响应判定，或服务端只判"订单存在"不判"金额已付"。
- **动作**：把响应里的 `status:false→true`、`code:401→200`、订单状态码改成已支付；或支付失败后**改大金额用同一订单号**重新拉起支付（`36-交易支付逻辑漏洞小总结` 案例 1：服务端不重核实际金额）。
- **案例锚点**：`97-web漏洞挖掘之业务逻辑漏洞`。

### 2.7 订单替代 / 订单复用

- **成因**：支付与订单的绑定关系不严（B 单号可给 A 单用），或旧订单支付后不销毁。
- **动作**：用低价订单号承接高价商品；取消优惠券后旧订单仍按优惠价可付。
- **案例锚点**：`微博优惠券无限复用`（**先扫码进支付页再点"不使用优惠券"**，券退回但订单已按优惠价锁定——顺序错了会报订单错误）；`百度文库连续包月存在支付漏洞`（取消签约后刷新，旧订单可重付，VIP 时长叠加）。

### 2.8 附属值篡改（运费 / 券 / 积分 / 赠币）

- **成因**：总额公式里除单价×数量外的项（运费、优惠、积分抵扣、赠送）未逐一校验。
- **动作**：改运费为 0、改优惠券金额/数量、`t_coin_gift` 改大直接白送。
- **案例锚点**：`支付逻辑漏洞.pdf`（`t_coin_gift=10` 白送币；改运费；`totalPrice=0`）。

### 2.9 类型字段替换

- **动作**：成人票 980 → 儿童票 380；同类还有"套餐类型 / 服务等级 / 区域"字段替换后按低价出单。
- **案例锚点**：`支付逻辑漏洞.pdf`。

### 2.10 加密 / Base64 订单篡改

- **成因**：订单参数整体加密或 Base64 编码后提交，但服务端仍信任其中字段。
- **动作**：解密 → 改配置（如 `vm_bandwidth=200`）→ 重新编码 → 提交，实现**低价买高配**。
- **案例锚点**：`支付逻辑漏洞.pdf`（云主机订单 order 字段）。

### 2.11 收银台 / 二维码生成接口重放

- **成因**：`getqrpaycode` 一类生成支付二维码的接口无次数限制、不幂等，且**不退出活动页即可反复创建订单**。
- **动作**：Repeater 重放 → 拿到新支付路径（形如 `/qrbe/19YU9pM`，末 6 位不同，可爆破）→ 每单付优惠价 → VIP 到期时间不断叠加。
- **案例锚点**：`某厂家文库活动存在支付漏洞`（`/cashier/interfacev2/getqrpaycode`、`goods_id=30001`）；`百度文库连续包月存在支付漏洞`（`is_new_user=1`）。

### 2.12 支付接口替换（改不存在的支付接口 / 通道）⚠️ 待实战验证

> 来源：14 类清单第 ⑥ 类，原报告**只给了"支付接口替换（改不存在接口）"这一句**，未给实例与字段名。以下为按成因推导的判定动作。

- **成因假设**：下单/支付请求里带"支付通道标识"（`payChannel` / `payType` / `payMethod` / 支付接口 URL），服务端按分支处理；当传入一个**它不认识的分支**时，走 `default` 兜底——而兜底分支可能被写成"无需校验、直接置成功"。
- **判定动作**：
  1. 找一个支付请求，把通道字段改成任意不存在的字符串（如 `payChannel=xxxtest`、`payType=9999`），或直接把支付接口路径替换成同域下不存在的路径；
  2. 观察响应：若返回**业务成功/订单已完成**而不是"通道不存在/参数错误"，即为命中；
  3. 复核：看订单状态是否真的变为已支付、权益是否到账（**只做无害验证，不实际套取权益**）。
- **为什么值得测**：这是 ② 改支付状态的"服务端版"——前者改响应，这里是让服务端自己走进错误的成功分支，属于典型的**异常分支兜底过宽**。
- **定级**：若可达"未付款拿到已支付权益"，高。
- **状态**：本库暂无命中案例，**属推断项，实战命中后请回填本节**。

### 2.13 重复支付 / 试用卡重复领取 ⚠️ 待实战验证

> 来源：14 类清单第 ⑦ 类"重复支付（试用卡）"，原报告未展开。与 2.5 限购绕过、4.1 首单复用的区别在于：**这里的对象是"试用/体验类资格"本身**。

- **成因假设**：试用卡、体验金、0 元购、7 天 VIP 这类"零成本或低成本资格"，服务端常只校验"当前是不是新用户"，**不校验"这个资格是否已领过"**，且领取动作不落唯一索引。
- **判定动作**：
  1. 正常领一次试用资格，抓"领取/开通/下单"包；
  2. Repeater 原样重放 5~10 次，看每次是否都返回成功、权益是否叠加（到期时间是否累加）；
  3. 与 3.3 的并发组合：重放 + 并发，成功率更高。
- **与 4.1 的关系**：4.1 是"首单优惠"（价格维度），2.13 是"资格本身可重复领取"（次数维度）。**两者常同时成立，写报告时合并成一个完整链路更有说服力**。
- **定级**：中（可叠加时长时升为高）。
- **状态**：本库暂无独立的试用卡案例（相近的是 4.1 与 2.5），**属推断项**。

### 2.14 盲盒 / 抽奖改 id 抽隐藏款 ⚠️ 待实战验证

> 来源：14 类清单第 ⑬ 类"盲盒改 id 抽隐藏款"，原报告未展开。

- **成因假设**：盲盒/抽奖/扭蛋类业务，"抽到哪一款"由**服务端随机**决定但结果写入时用了**客户端传入的商品 id**，或开盒接口直接接受 `goodsId/itemId/skuId` 且未校验该 id 是否属于该盒池。
- **判定动作**：
  1. 抓"开盒/抽奖"请求，找 `goodsId` / `itemId` / `skuId` / `boxId` / `poolId`；
  2. 把它替换成**同盒池内隐藏款/高价款的 id**（id 通常可从商品列表接口、`swagger`、前端 JS 或历史响应里拿到；若 id 自增可直接 ±1 遍历）；

- **另一种形态（更常见）**：抽奖结果先由服务端返回给前端、再由前端"提交结果"落库——这时候直接**改结果响应包**即可（归入 ② 改支付状态的同类成因"服务端信任客户端提交"）。
- **定级**：中~高（取决于隐藏款价值与可批量性）。
- **状态**：本库暂无命中案例，**属推断项**。

### 2.15 直播打赏遍历礼物 id ⚠️ 待实战验证

## 3. 并发竞态类

### 3.1 成立条件（缺一不可）

1. 操作有**状态变更且结果可累加**（领券、下单、领积分、点赞、开票、建房）；
2. 服务端校验与写入**不在同一原子区间**（无分布式锁 / 无唯一索引兜底）；
3. 校验发生在**请求处理早期**（比如"是否已领取"在业务开始前查，写在后）；
4. 请求**可被同时释放**（无随机 nonce 导致每次参数不同）。

### 3.2 Turbo Intruder 标准流程

1. 正常操作一次，抓包（**建议先成功 2 次以上再并发**，见 3.4）；
2. 右键 `Send to Turbo Intruder`，选 `race.py`；
3. 在请求包任意位置插入 `%s`（作为 payload 占位）；
4. 设置 `concurrentConnections`（实战常用 30，转账类案例用到 40）；
5. 执行 → 刷新页面看数量/次数是否被放大。

**race.py 关键机制**（多篇案例都点到的 `gate` 同步释放）：

```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=30,
                           requestsPerConnection=100,
                           pipeline=False)
    for i in range(30):
        engine.queue(target.req, gate='race1')
    engine.openGate('race1')      # 同一时刻释放，制造竞态窗口

def handleResponse(req, interesting):
    table.add(req)
```

#### 3.2.1 变体一：双 gate（多端点 / 多步竞态）

适用"一步准备、一步生效"的场景（先建订单 → 再支付核销；先加购物车 → 再下单），或第 12 章提到的"单包多端点攻击"。核心是**两个 gate 分别控住两个阶段，最后一刻同时开第二道**：

```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=30,
                           requestsPerConnection=100,
                           pipeline=False)
    # 阶段一：先排队 N 个"准备"请求，统一释放
    for i in range(20):
        engine.queue(target.req, gate='prepare')
    engine.openGate('prepare')
    # 阶段二：准备完成后再统一释放"生效"请求
    for i in range(20):
        engine.queue(target.req2, gate='fire')   # 需自行把第二个请求模板传进来
    engine.openGate('fire')
```

更完整的双端点模板见 `race-condition-test.md` §5.2（Multi-endpoint, same gate）与 §12（Single-packet multi-endpoint：state-check + state-mutate、cross-resource、auth 校验 + 特权动作三种模式）。

#### 3.2.2 变体二：`concurrentConnections` / `requestsPerConnection` 调优经验值

| 参数 | 建议值 | 说明 |
|------|--------|------|
| `concurrentConnections` | **20~30**（常用 30）；资金/转账类案例用到 **40** | 超过 50 多数站点开始出现连接失败、限频或 RASP 拦截，**收益递减甚至归零**；先从 20 起逐步加，找到"成功率最高"的档位 |
| `requestsPerConnection` | HTTP/1.1 下 **≥ 并发数**（脚本默认 100）；HTTP/2 单包攻击下可设 **1** | 保证每个连接上的请求能一次排完，避免分批导致到达时间被拉开 |
| `pipeline` | 保持 **False** | 设为 True 时部分中间件会把请求串行处理，**反而破坏竞态窗口** |
| 校验脚本是否真并发 | 看响应**时间戳分布是否集中** | 集中在一小段 = 真并发；呈阶梯状增长 = 被锁/被串行了（判别法见 `race-condition-test.md` §3.3 与 §7 防护检测） |

#### 3.2.3 变体三：请求带随机参数时的并发规避（对应 3.4 失败原因 ③）

**问题**：包里带时间戳 / 订单号 / nonce 时，每个请求参数都不同，服务端视为不同业务，构不成竞态。

按下面顺序逐级尝试：

1. **统一成固定值**：先把所有随机字段改成同一个固定值（同一时间戳、同一 nonce）再并发。若服务端不校验唯一性，直接命中——这是成本最低的一招。
2. **预生成一批合法随机值**：服务端确实校验 nonce 唯一性时，先批量生成 N 个合法 nonce/订单号，用 Turbo Intruder 的 `%s` 占位 + 字典把 N 个值喂进去，**参数各不相同但都合法**，仍有同时到达的窗口。
3. **拆成"批量准备 + 同时提交"两步**：订单号来自上一步响应时（最常见），先串行/并发地**下单 N 次拿 N 个订单号**，再把 N 个"支付/核销"请求挂在同一个 gate 上一把放出。这一步正是 3.2.1 双 gate 的用武之地。
4. **换传输层减少抖动**：改用 HTTP/1.1 末字节同步（last-byte sync）或 HTTP/2 单包攻击，把网络抖动造成的到达时间差压到最小——命令与用法见 `race-condition-test.md` §3（h2load）与 §4。
5. **校准后再打钱相关接口**：如果仍然失败，**先用 3.3 里已验证能成的功能点（如点赞/阅读量这种无防护的）跑一遍**，确认脚本和链路没问题，再回去打领券/下单——分不清"脚本问题"和"业务本身无竞态"是新手最常见的误判，会白白漏掉真洞。

### 3.4 并发失败的 4 个原因（`逻辑漏洞-月神.pptx` 第 03 节原话归纳）

1. **网络差**——不一致的到达时间会吃掉竞态窗口；
2. **未先成功 2 次**——需要基本操作成功 2 次以上才满足并发条件；
3. **请求带随机参数**（时间戳、订单号、nonce）——每个包参数不同，服务端视为不同业务，构不成竞态；
4. **防护中间件**（频率限制、RASP）——需先确认拦截点。

## 6. 密码重置类

### 6.1 五类成因（`35-密码找回逻辑漏洞小总结` 原文归纳）

1. 凭证/Tool 直接回显到前端，或弱算法（基于时间戳、userid 可猜）；
2. 前端校验，改返回包即绕过；
3. 最后一步改密**未校验该账号是否通过验证**、短信与手机号是否对应；
4. 分步流程可**跳过步骤直达最后一步**；
5. 身份参数（uid / session）可替换。

### 6.2 分步流程跳步 / 响应篡改

`重置密码逻辑漏洞`：验证码校验接口 `verify_code` 只返回 `{"status":1,"msg":"验证码验证通过"}`，**不返回任何后续校验凭证**，于是把 `status:0→1` 直接进入重置页改任意用户密码。

### 6.3 uid / 身份参数越权改密

`逻辑漏洞另类小技巧.pdf` 四连（同一目标 `FindPwd.aspx` 系列）：

- 账户名 FUZZ 时**普通用户手机号完整回显**，改 `phone` 为自己号收码（发码不校验手机号唯一性）；
- `ForgetResetPassword?uid=223` → `uid=1` 切用户，遍历 uid 改密且回显用户名；
- `POST /Login/ForgetResetPassword` 带 `NewPwd=...&uid=194`，**无需验证码直接改任意用户密码**；
- 忘记密码入口虽被删，后台地址直访仍在（只删了跳转没删功能），配合弱密保问题 `123456` 直达设新密。

### 6.4 注册激活凭证回显 → 任意注册

`任意注册`：`POST /ser/register` 的响应直接返回 `active:YWN0aXZFX2NvZGU9...`（Base64 激活码），拼接 `/?active=...` 即完成注册，**绕过邮箱验证**。

### 6.5 学号 / 账号回显链

`验证码回显`（铜陵职院平台）：`getUserNumByBindMail` 用邮箱反查**学号**，`sendMailGetCode` 回显**验证码** → 改密一条链走完。

### 6.6 通用检测动作

用户名爆破时**开 Burp 逐包看响应**；找回密码关注三处：手机号/邮箱唯一性校验、uid 是否可控、是否存在"未授权改密"接口。

## 15. 去重可信度验证记录（2026-09-14 抽验）

**质疑**：文件副本可能只是文件名重复，内容未必一样——若把不同打法误判为重复合并，就会漏收录。为验证，抽取了 4 组、共 13 份文档做**逐段内容比对**（非仅看标题或开头）。

| 组 | 抽样 | 大小关系 | 实测结论 | 是否遗漏手法 |
|----|------|---------|---------|-------------|
| G1 | 序号 1 `0到1逻辑漏洞-支付篇` / 57 `支付漏洞_(1)` / 58 `支付漏洞2` | 三者均为 **537278**（大小完全相同，但**标题完全不同**） | **逐字完全相同**（含 6 张图片 alt 文本），仅文件名与解压临时路径等元数据不同 | 无 |
| G4 | 序号 5 `21-聊聊暴力破解.pdf` / 6 `..._20210506214052.pdf` | 同为 **1629101** | **逐字完全相同**，时间戳副本 | 无 |
| G2 | 序号 64 `时间校验漏洞` / 65 `_(4)` / 66 `_(5)` | 1600259 / **663352** / 1828753（相差 2.4 倍） | **实质相同**，差异仅为**配图分辨率与数量**（65 是低清精简版）、"随心卡/vip"叫法不同 | 无 |
| G3 | 序号 97 `限制购买逻辑漏洞` / 98 `_(3)` / 99 `_(4)` | 2185949 / 1745026 / **2084632** | **实质相同**，均含两个案例（百度智能云学生套餐突破限购 1 台 + 云盘会员差价批量刷单）；差异仅为**厂商名匿名化**——99 显式写"百度智能云"，97/98 写"某厂商/某智能云" | 无（唯一信息差是 99 保留真实厂商名，已采信） |

**结论**：

1. **`file_size` 完全相同 ⇒ 内容逐字相同**（G1、G4 证实）。G1 尤其反直觉——三份标题完全不同的文档，大小一致即内容一致，属同一篇文章改名存多份。
2. **`file_size` 不同 ≠ 内容不同**：大小差 2 倍以上的（G2、G3）仍只是配图与厂商名差异，未出现"伪装成副本的不同报告"。**本次未发现任何因去重而漏收录的打法。**
3. 因此按"标题 + 大小"去重是**安全的**，且我采用的是保守策略：**大小不同的一律逐份实读**，宁可多读也不合并（`时间校验漏洞` ×3、`限制购买逻辑漏洞` ×3 都是实读后确认同源的）。
4. **唯一存疑项**：序号 54（读取失败，见第 14 章）——无法验证，已在索引中保留独立条目而未合并进 53。

**给后续维护的建议**：ima 里的副本多为"同一篇报告多次投稿/多平台备份"的副产品，检索时按"标题主干 + 大小"去重即可；真正需要警惕的不是副本，而是**同一标题下的不同版本**（如 G2 那种低清版），所幸本次证实它们内容等价。
